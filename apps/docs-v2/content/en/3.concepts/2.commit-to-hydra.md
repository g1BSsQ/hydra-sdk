In hydra-node v2, **the Head opens directly after `Init`** with an empty UTxO set. There is no initial commit phase. Funds enter an already-open Head through **incremental deposits** on Cardano Layer 1 (L1); they become spendable on Layer 2 (L2) only after the increment is finalized.

## Head lifecycle and deposits

- `bridge.commands.init()` requests Head initialization; `HeadIsOpen` signals that the Head is open. It does not contain a `utxo` field; use `bridge.querySnapshotUtxo()` to query the snapshot UTxOs.
- A deposit is a separate L1 transaction targeting an `Open` Head. Depositors need not deposit at the same time or be Head participants.
- `bridge.commit(...)` uses `POST /commit` to **draft** a deposit transaction. It does not sign, submit, confirm, or finalize the transaction.

## Deposit lifecycle

1. `POST /commit` returns an **unsigned draft** with `cborHex`.
2. The owner signs the complete L1 transaction, submits it to Cardano L1, and waits for on-chain observation. `bridge.submitCardanoTransaction(...)` is an optional SDK submission path; `TransactionSubmitted` only acknowledges submission, not chain confirmation.
3. `CommitRecorded` reports the observed L1 deposit (`pendingDeposit` is its transaction ID). Funds are **not yet spendable** in the Head.
4. `DepositActivated` reports that the deposit is mature/eligible for inclusion (`depositTxId`).
5. `CommitApproved` indicates approval through a snapshot (`utxoToCommit`); this event has **no `depositTxId` field**.
6. `CommitFinalized` (`depositTxId`) follows observation of the on-chain increment transaction. Only then treat the deposited UTxOs as available on L2. Chain rollbacks may require re-observation.

## SDK example: draft, sign externally, submit on L1

The following uses the default WebSocket connector and real `@hydra-sdk/bridge` methods. Pass actual, unspent wallet-owned L1 UTxOs as `UTxOObject`. **Supply your own L1 signer**: `signOnL1` is a callback parameter, not an SDK API, and must return the *complete witnessed transaction CBOR*, not just witnesses. This is an integration skeleton, not a runnable end-to-end wallet example.

```ts
import { HydraBridge, HydraHeadStatus, HydraHeadTag } from '@hydra-sdk/bridge'
import type { UTxOObject } from '@hydra-sdk/core'

const bridge = new HydraBridge({ url: 'ws://localhost:4001' })
bridge.events.on('onMessage', event => {
  if (event.tag === HydraHeadTag.CommitRecorded) console.log('Recorded:', event.pendingDeposit)
  if (event.tag === HydraHeadTag.DepositActivated) console.log('Activated:', event.depositTxId)
  if (event.tag === HydraHeadTag.CommitApproved) console.log('Approved head:', event.headId)
  if (event.tag === HydraHeadTag.CommitFinalized) console.log('Finalized:', event.depositTxId)
  if (event.tag === HydraHeadTag.DepositExpired) console.log('Expired:', event.depositTxId)
})
await bridge.connect()

async function depositUTxO(
  utxoToCommit: UTxOObject,
  signOnL1: (unsignedCborHex: string) => Promise<string>
) {
  if ((await bridge.headInfo()).headStatus !== HydraHeadStatus.Open) throw new Error('Head must be Open')
  const draft = await bridge.commit({ utxoToCommit })
  if (!draft) throw new Error('No deposit draft returned')
  const signedCborHex = await signOnL1(draft.cborHex)
  const result = await bridge.submitCardanoTransaction({
    type: 'Witnessed Tx ConwayEra',
    description: 'L1 incremental deposit',
    cborHex: signedCborHex
  })
  if (result?.tag !== 'TransactionSubmitted') throw new Error('L1 submission not accepted')
  return result
}
```

::warning
Do not treat the result of `bridge.commit()` or `TransactionSubmitted` as a completed deposit. Track the matching deposit transaction on L1 and wait for `CommitFinalized`; a connection or node-sync failure may interrupt the observed event stream.
::

## Request formats and practical limits

- **Simple request:** `bridge.commit({ utxoToCommit })` commits the whole specified UTxO set; the SDK type is `SimpleCommitBody`.
- **Blueprint request:** `bridge.commit({ blueprintTx, utxo, changeAddress })` accepts a `Transaction` envelope in `blueprintTx`, an `UTxOObject` in `utxo`, and optional `changeAddress`. Outputs select what enters the Head; with a change address the node balances and returns the remainder to L1. Without one, output-bearing blueprints must already balance.
- Provide spendable Shelley-era UTxOs (Byron addresses are rejected), the required signing keys or script witnesses, adequate L1 fees and minimum ADA for deposited outputs, and matching chain/network data.
- Deposits must fit ledger transaction and serialized output-value limits; oversized deposits can fail with `DepositTooLarge`. Values cannot exceed the supplied inputs. Blueprint transactions should not include stake-pool/DRep registration or delegation certificates.
- A deposited UTxO's reference script is **not preserved on L2**. Verify script/datum behavior for your use case. Deposit activation and recovery deadlines are controlled by node/protocol configuration, not by a fixed SDK timeout.
- Check `bridge.syncedStatus`: a node reporting `CatchingUp` can reject client inputs. **Connector caveat:** the `HexcoreConnector` `commit` implementation still has a blueprint `TODO` and uses a gateway-specific payload; do not assume the blueprint request above works there.

## Expired deposits and recovery

If a deposit is not incremented before its deadline, `DepositExpired` provides `depositTxId`. After the on-chain deadline, `await bridge.recoverDeposit(depositTxId)` requests recovery on L1 (`DELETE /commits/{txId}`); it does **not** add funds to L2. Recovery remains possible for unclaimed deposits even after the Head closes or fans out. Confirm recovery on L1 before considering funds returned.

`await bridge.pendingDeposits()` queries `GET /commits` and returns **transaction ID strings**, not UTxO objects. The SDK may fall back from `recoverDeposit()` to the WebSocket `Recover` command if a custom connector lacks HTTP recovery; in that case it does not return the HTTP outcome.
